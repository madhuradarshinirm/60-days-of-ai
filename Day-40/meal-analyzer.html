How this was built

The system prompt ("brain")

The assistant is scoped narrowly to nutrition feedback on a single described meal. It's instructed to reason like a registered-dietitian-style coach: encouraging but honest, never fear-based, and never diagnosing. Key design choices:

  • Structured JSON output — the model is told to return only JSON matching a strict schema (verdict, calories, macros, summary, pros, cons, flags, recommendations). This lets the UI render a real dashboard instead of parsing prose.
  • Estimation transparency — since no food database is wired in, the prompt instructs the model to give clearly-labeled estimates based on typical portion sizes and ingredients, not fake precision.
  • Edge cases handled explicitly: empty/nonsense ingredient input → asks for real food input via the JSON's summary field with verdict:"unclear"; medical questions or requests for diagnosis → redirected to a professional, never answered clinically; abusive input → calm, brief refusal, no meal data required.
  • Tone lock — explicit instruction to sound like a friendly, encouraging coach: never shaming or moralizing about food ("bad" foods), always pairing any criticism with a specific, doable improvement.

Why the UI looks like this

Generic AI tools default to a plain chat box. A meal analyzer isn't a conversation — it's closer to a lab result or a restaurant receipt. So the output renders as a ticket-style report (dashed divider, receipt framing) with a calorie + macro ring cluster as the signature visual, echoing how nutrition labels actually communicate: fast numbers first, detail after. The palette (deep forest ink, leaf green, citrus, muted berry) is drawn from produce and kitchen materials rather than a generic tech gradient, and the ingredient field behaves like a real tag input so the form itself feels food-specific, not like a generic survey.

Extending this

  • Real nutrition data: swap the model's estimate for a tool call to a food database API (e.g. USDA FoodData Central) via an MCP server or a second fetch step, then have Claude reason over verified numbers instead of estimating.
  • Memory across meals: persist each report (localStorage or a backend) and pass a daily/weekly summary back into the prompt so feedback can reference "this is your 3rd high-sodium meal today."
  • Multi-step flow: turn portion-size or ambiguous-ingredient questions into a quick clarifying follow-up before generating the final report, instead of guessing.
  • Image input: accept a photo of the plate and use Claude's vision input to identify ingredients automatically, pre-filling the tag list for the user to confirm.
